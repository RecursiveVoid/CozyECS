# CozyECS benchmark results

Generated by `npm run benchmark` on 2026-10-07; hand-written sections noted in the Summary.

## Summary

Run on 2026-10-07 (label `refresh_2026-10-07`). CozyECS's fastest form is #1 in all five
scenarios at the median. The iteration margins are narrower than in the 2026-09-17 audit run,
because harmony-ecs measured faster this time (packed_5 466k against 430k), not because CozyECS
got slower.

## Methodology

```
node benchmarks/benchmark.js --paired --repeats=5 --time=2000 --warmup=500 --min-ref=0.85
```

- **One process per job.** Every (scenario, variant) job runs in its own `node` process
  (`benchmarks/worker.js`), so JIT state and type feedback never leak between libraries.
- **Benchmark first, verify afterwards.** Each job benchmarks the first world created in its
  process. Steady-state scenarios are re-checked after the benchmark. The variant is then
  verified on a fresh world (3 ticks, then the full state is checked). A job that fails
  verification is reported as "wrong result".
- **Timing:** 500 ms warm-up, then 2000 ms of measurement. `step()` is called through the
  `mega` batch runner, which is the same for all libraries.
- **Repeats:** the full list of 70 jobs is run 5 times, in a freshly shuffled order each time
  (seed 1449093231). The tables report the **median** of the 5 repeats.
- **Paired ratios:** in each repeat, every variant's ops/sec is divided by the fastest correct
  non-CozyECS variant from the same repeat. The median of those ratios is reported.
- **Slow-core guard:** every job also times a fixed CPU reference kernel. A job whose reference
  speed falls below 0.85 x the best seen in the run (because it landed on an efficiency core or
  a contended CPU) is re-run, up to 2 times. **This run took 89 re-runs and 22 jobs were still
  flagged slow afterwards** (2026-09-18 round 2: 58 re-runs). A flagged job is excluded from the
  pairing for its repeat, which is why one `cozyecs (direct)` frag_iter repeat and one wolf-ecs
  add_remove repeat are missing from the ratios below.
- **Idiomatic adapters.** Each adapter iterates the way that library's README shows. Typed
  libraries use `f32` fields and object libraries use JS numbers. Entity counts and the work per
  op are the same across adapters.

### Scenarios

- **packed_5**: 1000 entities with A..E ({value}). 5 systems, each doubling one component.
- **simple_iter**: 4 archetypes x 1000 entities (P+V, P+V+A, P+V+B, P+V+A+B). 1 system does P += V.
- **frag_iter**: 26 components A..Z, with 100 entities per letter, each having [Letter, Data].
  1 system doubles Data (2600 entities in 26 archetypes).
- **entity_cycle**: 1000 entities with A. Per op: spawn one B-entity per A, then destroy every
  B-entity.
- **add_remove**: 1000 entities with A. Per op: add B to every A, then remove B from every B.

### CozyECS variants

- `cozyecs`: function systems with chunk loops, run by `world.update()`. Structural changes go
  through the command buffer.
- `cozyecs (direct)`: raw chunk loops with immediate structural changes.
- `cozyecs (forEach)`: `query.forEach` callbacks.

### Extra competitor variant

- `bitecs4 (cached query)`: bitecs 0.4 rebuilds a string key (map/sort/join) on every
  `query(world, terms)` call. This variant keeps the stable array returned by `query()` and calls
  the exported `commitRemovals()` once per frame. `bitecs4` is the documented usage.

## Fairness fixes

The benchmarks were audited before the 2026-09-17 run and the fixes have been in place for every
run since, including this one. Nothing in `src/` changed; all fixes are in `benchmarks/`. To see how much each fix mattered, the old and new harness were run back to back
(3 rounds each, 1 s per job):

| job | old harness | new harness | change |
|---|---:|---:|---:|
| becsy packed_5 | 8,719 | 82,004 | 9.4x |
| perform-ecs packed_5 | 20,304 | 169,640 | 8.4x |
| geotic packed_5 | 14,998 | 77,265 | 5.2x |
| ecsy packed_5 | 10,815 | 18,439 | 1.7x |
| bitecs simple_iter | 248,640 | 342,308 | 1.38x |
| wolf-ecs simple_iter | 247,697 | 344,938 | 1.39x |
| becsy simple_iter | 10,060 | 14,006 | 1.39x |
| cozyecs (all variants), harmony-ecs, bitecs4, javelin | | | about 1.00x |

1. **Verification world polluted type feedback (the biggest effect).** Each job used to verify
   correctness on its own world *before* building the benchmark world. V8 shares type feedback
   between closures and classes created by the same source line, so the verification world
   left the benchmark code polymorphic. This hurt libraries with a class per component (becsy,
   ecsy, geotic, perform-ecs) and adapters that capture typed arrays in closures (bitecs,
   wolf-ecs). CozyECS defines its components once for the whole process, so it was never
   affected. Now the benchmark runs on the first world created, and verification runs afterwards
   on a fresh world.
2. **Shared system body in packed_5.** The adapters for becsy, ecsy, geotic, perform-ecs and
   javelin built their 5 systems from one loop. That single line of code saw 5 component classes,
   which made property access there slow. Each of these adapters now has 5 hand-written systems,
   as a real app would.
3. **bitecs 0.4 query cost.** Added the `bitecs4 (cached query)` variant (see above) next to the
   documented usage. On packed_5 it goes from 234.9k to 370.7k ops/sec.
4. **Development-mode checks.** ecsy runs extra checks unless `NODE_ENV=production`, so every
   benchmark and memory process now sets it. ecsy still reads `process.env` on some paths, which
   costs it a little in Node. It is far behind in every scenario either way.
5. **Memory warm-up.** bitecs 0.3 was the only library measured without the small warm-up world,
   because its entity ids are global to the process. It now calls `resetGlobals()`, so the
   warm-up can run.
6. **Memory queries.** Some adapters used to hold a query in the memory test and others did not.
   Every library now holds one Position+Velocity query.
7. **Checked, no change needed:**
   - Field types: every typed library uses `f32`, and object libraries use JS numbers.
   - Entity counts and work per op match across adapters. In add_remove, javelin takes two steps
     per op because its changes apply one step late. That is the same amount of work.
   - Every job gets the same process isolation, warm-up and batch runner.
   - Adapters iterate the way each library's README shows. becsy uses its perf build.
   - CozyECS adapters have the strictest verification of all adapters: every value, the chunk
     layout and the live entity count are checked. Their structural changes really happen.
   - perform-ecs's add_remove failure is a genuine leak in that library:
     `removeComponentsFromEntity` never removes the entry from `entity.components`, which held
     6,888 entries after the benchmark.

## Shared buffer (`new World({ shared: true })`)

*(Measured in the 2026-09-17/18 rounds and carried over; `shared` was not re-measured on
2026-10-07.)*

`shared: true` allocates each archetype table as a `SharedArrayBuffer` instead of an
`ArrayBuffer`. The two builds were compared with isolated, shuffled, paired runs (5 repeats in
round 4, 4 repeats in round 3, 1 s per job). Each cell is the median of shared ÷ plain:

| scenario | `cozyecs` r4 | `cozyecs (direct)` r4 | `cozyecs` r3 | `cozyecs (direct)` r3 |
|---|---:|---:|---:|---:|
| packed_5 | 1.00 | 1.00 | 1.00 | 0.99 |
| simple_iter | 1.00 | 1.00 | 1.00 | 1.00 |
| frag_iter | 1.00 | **0.91** | **0.94** | 0.99 |
| entity_cycle | 1.00 | 1.02 | 1.00 | 1.02 |
| add_remove | 1.00 | 0.99 | 1.00 | 0.94 |

- Most cells are within ±2%, which is run-to-run noise. frag_iter lost 6–9% in one variant in
  each round, though not in the same variant both times. In round 4 the loss was consistent:
  `direct` measured 827k–846k shared against about 920k plain in 4 of 5 repeats. The 0.94 on
  add_remove (direct) in round 3 did not show up again in round 4. Treat many small shared
  chunks as possibly a few percent slower.
- Memory is the same: 26.2 B/entity and 12 ms creation time with or without `shared`.
- The default is `shared: false`. Turn it on only if you hand columns to workers.

## Where CozyECS is not #1

- **frag_iter, repeat 3: harmony-ecs beat every CozyECS form.** harmony-ecs reached 889,792
  ops/sec against 845,196 (systems), 827,411 (direct) and 686,782 (forEach) in that repeat, a
  paired 0.95 for the best form. This is new; in the 09-17 run frag_iter stayed above 1.00 in
  all five repeats. The other four repeats are 1.04-1.10, so the median is still 1.08, but
  frag_iter has joined packed_5 as a scenario CozyECS can lose in a single run.
- **frag_iter, `cozyecs (direct)`: 0.95 of harmony-ecs (was 1.11).** The raw chunk loop no
  longer beats harmony-ecs on the 26-archetype scenario at the median. Only the function-system
  form does.
- **simple_iter, `cozyecs (direct)`: 0.79 of bitecs (was 0.81).** The raw chunk loop outside a
  system is slower than bitecs (342.9k) and wolf-ecs (333.4k) here. The cause is in `src/`, not
  in the adapter: the same loop inside a function system reaches 411k. The `forEach` form wins
  this scenario by 1.07.
- **packed_5 and frag_iter, `cozyecs (forEach)`: 0.78 and 0.80 (was 0.85 and 0.87).** The
  callback form lost ground against harmony-ecs, and on packed_5 it is also behind wolf-ecs and
  `bitecs4 (cached query)`. Use chunk loops or `forEachChunk` when this matters.
- **packed_5 is close to a tie.** The margin is 1.05 (09-17: 1.12), with repeats spanning
  1.02-1.08. harmony-ecs at 466.3k is within 5% of CozyECS's 488.9k. It no longer wins a repeat
  outright, as it did on 09-17, but the lead is inside the run-to-run spread.
- **Structural changes inside systems cost 5-11%.** On entity_cycle and add_remove the systems
  variant reaches 95% and 89% of `direct`, because commands are queued and then flushed. (On
  09-17 the gap was 15-20%.) It is still 3.3x and 1.37x ahead of the fastest competitor.
- **Leads are narrow in iteration.** The margins are 1.05-1.19 on packed_5, simple_iter and
  frag_iter, and the spread across repeats is about 10%, so a single repeat can swing the order,
  and on frag_iter it did. The claim these numbers support is that CozyECS's best form is
  fastest in each scenario **at the median**. They do not support "every CozyECS API is the
  fastest", nor a reliable win in any one iteration run.

## Caveats

- **The machine was not quiet.** 14 of 48 load samples were above 6 and the peak was 10.27, with
  iCloud's `bird` holding about a core throughout. The shuffled pairing and the slow-core guard
  absorb much of this (89 re-runs happened), but 22 jobs stayed flagged, and the function-system
  variant still varied from 342k to 418k on simple_iter.
- **add_remove's 5th repeat is an artifact, not a 3x win.** The paired ratios in that repeat
  (systems 2.47, direct 3.01) look like a jump, but only because wolf-ecs's run was excluded by
  the slow-core guard and becsy at 16.1k became "best competitor". The four clean repeats give
  1.41-1.54, which is what the 1.53 median rests on.
- **`cozyecs (direct)` on frag_iter is a 4-repeat median**, for the same reason: one of its runs
  was dropped by the guard.
- Do not compare absolute ops/sec across rounds. This run's reference kernel is about 1.9x the
  2026-09-18 round-2 run's, so every library's ops/sec here is roughly double that round's.
  Compare the paired ratios instead.
- These are micro-benchmarks of five fixed workloads on one CPU and one Node version. Measure
  your own workload.

## Reproducing

```
npm run build
npm run benchmark -- --paired --repeats=5
```

Use `--scenario=`, `--lib=` and `--variant=` to run a subset, and `--quick` for a noisy smoke
test. `benchmarks/benchmark.js` lists every option. Running the benchmark regenerates this file.

### GPU / kernel: notes (written by hand for the 2026-10-07 refresh)

**The section above is regenerated.** `node benchmarks/gpu.js --write` replaces everything between
the `gpu-kernel` markers. These notes are outside the markers, so they are kept. The table was
measured as two invocations (`--kernels=simple --json=...`, then `--kernels=gravity --json=...`)
and rendered with `--from-json=simple,gravity --write`.

**Per-kernel load (the generated header's load line is only the gravity run's).** `--from-json`
takes `load0` from the earliest run and `load1` from the last file, so the "6.4 / 6.9 / 6.3 ->
4.3 / 5.9 / 6.1" line above describes gravity only. Actual loads:

| run | 1-min load at start | at end | used for the tables |
|---|---:|---:|---|
| `simple`, first run | 5.5 | **9.7** | no (superseded) |
| `simple`, confirmation | 3.6 | 3.3 | **yes** |
| `gravity` | 6.4 | 4.3 | yes |

The first `simple` run ended with the 1-minute load at 9.7, so it was re-measured on a quiet
machine and the confirmation run is what the tables show. The two agree closely, which is the
main reason to trust these break-evens: `none` 117.5k vs 123.0k and `async` 123.3k vs 133.9k
(within 8%), `sync-frame` ">1M" vs 999.8k. Per-cell medians also sat close to their minima
(kernel-cpu spread 1.18-1.49x max/min across the 5 processes), so the high outliers are isolated
contaminated repeats that the median absorbs.

**GPU:** Dawn, through the `webgpu` npm package (0.6.1) on the M4's integrated GPU. A GPU frame
calls `world.update(dt)` and then yields once to the event loop. `sync-frame` also awaits
`flushKernels(world)`. The `none` and `async` runs are drained with `flushKernels` after every
timed batch, inside the clock, so the reported ms/frame includes the final drain.

**THE HEADLINE: the CPU got ~1.9-2.4x faster and the GPU floor did not, so every break-even
roughly doubled.** This settles the question the round was run to answer.

| | 2026-09-18 round 2 | 2026-10-07 | change |
|---|---:|---:|---:|
| `kernel-cpu` simple @ 1M | 1.80 ms | 0.932 ms | **1.93x faster** |
| `kernel-cpu` simple @ 100k | 0.149 ms | 0.061 ms | 2.44x faster |
| `kernel-cpu` gravity @ 1M | 2.70 ms | 1.42 ms | 1.90x faster |
| `kernel-cpu` gravity @ 100k | 0.271 ms | 0.138 ms | 1.96x faster |
| `gpu-none` floor (1k-10k) | 0.057-0.058 ms | 0.061-0.066 ms | ~5-14% *slower* |
| `gpu-async` floor | 0.071-0.083 ms | 0.065-0.074 ms | ~10% faster |
| `gpu-sync` floor | 0.35 ms | 0.23-0.40 ms | mixed |

The CPU backend improved substantially while the GPU's fixed per-frame cost stayed flat. The
break-even is the point where the CPU's per-entity cost pays back that fixed cost, so halving the
CPU's per-entity cost doubles the entity count needed.

**Break-even vs `kernel-cpu`.** Interpolated log-linearly between the measured sizes (1k, 10k,
30k, 50k, 100k, 300k, 1M), so treat these as rough figures:

| kernel | `none` | `async` | `sync-frame` |
|---|---:|---:|---:|
| simple (6 ops) | **117k** (09-18: ~49k) | **123k** (~65k) | > 1M (> 1M) |
| gravity (20 ops) | **51k** (~22k) | **56k** (~34k) | **684k** (~554k) |

- `sync-frame` still never pays off for `simple` up to 1M (0.971 vs 0.932 ms at 1M, a 4% loss).
- The GPU's fixed floor is about 0.061-0.067 ms for `none`, 0.065-0.074 ms for `async` and
  0.23-0.30 ms for `sync-frame`, flat from 1k to 50k.

**The `auto` defaults are now mis-fitted, and they switch to the GPU far too EARLY.** Measured
CPU cost in the 25k-100k break-even band, which is what the estimator is supposed to predict:

| kernel | measured ns/entity (30k, 50k, 100k) | mean | `estimateCPUNanosPerEntity` | estimator / measured |
|---|---|---:|---:|---:|
| simple (6 ops) | 0.583, 0.582, 0.614 | **0.593** | 0.91 | 1.53x too high |
| gravity (20 ops) | 1.353, 1.360, 1.380 | **1.365** | 1.82 | 1.33x too high |

The *ratio* between the two kernels is fine (measured 2.30x, estimator 2.00x). The problem is the
absolute level: both estimates are ~1.3-1.5x too high, so `BASELINE_CPU_NS_PER_ENTITY / estimate`
scales the thresholds *down* too much. Against the measured break-evens:

| kernel | mode | effective switch point | measured break-even | measured / effective |
|---|---|---:|---:|---:|
| simple | `none` | 56k | 117k | **2.08** |
| simple | `async` | 56k | 123k | **2.19** |
| simple | `sync-frame` | 877k | > 1M | (>1.14) |
| gravity | `none` | 28k | 51k | **1.83** |
| gravity | `async` | 28k | 56k | **1.98** |
| gravity | `sync-frame` | 438k | 684k | **1.56** |

**Every fire-and-forget switch point is now outside the 0.6-1.6x band this project has used as its
acceptance criterion** (the previous round's worst was 0.79). The practical consequence is the
mirror image of the round-1 bug: `auto` now moves a `simple` kernel to the GPU at ~56k entities
when the GPU does not actually win until ~117k, and a `gravity` kernel at ~28k when the real
crossover is ~51k. In that band `auto` picks the slower backend — at 50k, `simple` costs 0.029 ms
on the CPU and 0.067 ms on the GPU with `none`, so the wrong choice is about **2.3x slower**.

**Re-fit (APPLIED to `src/gpu/cpu.ts` and `src/gpu/runtime.ts` after this round, together with
docs/GPU.md, docs/GUIDE.md and the tests that pin the constants).** Setting the estimator to
the measured cost and raising the thresholds fits both kernels and all three modes consistently:

```
CPU_NS_PER_ENTITY_FIXED = 0.26   (was 0.52)
CPU_NS_PER_OP           = 0.055  (was 0.065)   -> simple 0.59 ns, gravity 1.36 ns
DEFAULT_AUTO_THRESHOLDS = { fireAndForget: 63_000, synchronous: 820_000 }
                                  (was 45_000 / 700_000)
```

That gives effective switch points of simple ~121k / ~1.58M and gravity ~53k / ~685k, i.e.
measured/effective of 0.97 (simple `none`), 1.02 (simple `async`), 0.98 (gravity `none`), 1.06
(gravity `async`) and 1.00 (gravity `sync-frame`) — every one within 1.06x, and simple
`sync-frame` correctly placed above 1M so it never switches. Two cautions: these constants track
one machine in one state, and this machine's own speed moved 1.9x in three weeks, which is the
best argument for `calibrateAuto(core)` (it measures the break-even on the user's device at
runtime) rather than for any particular default. As a cross-check, `calibrateAuto` run three times
on this device right after the re-fit returned `fireAndForget` 48k / 48k / 72k (and `synchronous`
255k / 402k / 780k), so the new 63k default sits inside the device's own spread; the old 45k sat at
its bottom edge. A re-fit should also re-check
`BASELINE_CPU_NS_PER_ENTITY = 1.14`, which was anchored to a 12-op kernel at 1.140 ms per 1M on
the older, slower machine state; only its ratio to the estimator matters, but the comment no
longer describes this machine. (Re-checked and KEPT at 1.14 in the applied re-fit: it is now
documented as a pure normalization anchor -- rescaling it and both thresholds by the same factor
is a no-op -- which avoids churning an exported constant for no behavioural change.)

**Correctness gate: every GPU cell passes, at every size, in every repeat** — 147 cells over the
three runs (two `simple`, one `gravity`), zero failures and zero errors. `staleReadbacks` is 0 in
every `async` process.

**Readback coalescing changed character, though `async` ms/frame still accounts for it.** Nearly
every dispatch now coalesces (simple at 1k: 12,429 of 12,834, i.e. 97%, against 7,223 of 11,051
= 65% on 09-18), and the final drain grew from 0.2-0.95 ms to **3.2-21.3 ms** (21.3 ms for
gravity at 1M). The drain happens inside the clock, so the reported `async` figures already pay
for it; but it means an app that stops dispatching has a larger one-off tail to flush, and the
1M `async` cells still spread widely across repeats.

**bitecs at 300k is still an outlier:** 0.742 ms (simple) and 1.10 ms (gravity), about 2.6x
slower than every CozyECS variant and slower per entity than bitecs at 1M. It reproduces in all
5 repeats. The likely cause is the harness's `setDefaultSize(1.1 n)` sizing of bitecs's sparse
set at that size. It is not a CozyECS result, so the 300k "vs bitecs" ratios (2.4-2.8x) are left
out of the claims here.

**CPU backend.** `kernelSystem({ target: 'cpu' })` is level with hand-written `forEachChunk` on
`simple` (within 2% at every size) and is 1.14-1.30x faster than bitecs from 1k to 100k and
1.18x at 1M. On `gravity` it is 1.04-1.15x bitecs, and it now beats `forEachChunk` by 2-8% from
30k up (1.42 vs 1.54 ms at 1M).

**Plain chunk loop (carryover issue B).** The plain `for (i < chunk.count)` loop over
`chunk.col()` is 0.79-0.87x bitecs on `simple` from 1k to 100k and 1.23x at 1M, where memory
bandwidth dominates — unchanged from the previous two rounds. On `gravity` the heavier body hides
the gap (0.98-1.05x up to 100k, 1.07x at 1M). `kernelSystem` and `forEachChunk` stay the
recommended fast paths (docs/INTERNALS.md, "Why the plain chunk loop trails closure-constant
loops").

**Stale numbers elsewhere in the repo.** These break-evens are quoted in `docs/GPU.md` (the
readback-mode table in section 3.3 and the "Calibration" table in section 4) and in
`docs/GUIDE.md` ("Measured break-even"). They still carry the 09-18 figures (~49k/~64k,
~23k/~34k) and should be updated together with any constant re-fit.
